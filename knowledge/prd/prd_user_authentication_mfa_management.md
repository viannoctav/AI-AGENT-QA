# PRD — User Authentication & Multi-Factor Authentication (MFA) Management

## 1. Document Information

**Product:** Core Identity Platform  
**Module:** User Authentication & Multi-Factor Authentication (MFA)  
**Document Purpose:** Complex QA test-case generation, coverage planning, traceability, and gap-analysis validation for AI-QA-Engineer V3.

---

## 2. Actors

- User / Account Owner
- Authentication Service
- MFA Provider (SMS / Authenticator App / Email OTP)
- Audit & Security Logging Service

---

## 3. Feature Overview

User can register an account, log in using primary credentials (email/username and password), configure and manage Multi-Factor Authentication (MFA) methods (Authenticator App TOTP, SMS OTP, Backup Codes), complete step-up authentication upon detecting high-risk actions or logins, reset credentials, and manage active sessions.

The authentication system must prevent unauthorized access, brute-force credential guessing, replay attacks, session hijacking, invalid state transitions, and unauthorized MFA bypass beyond configured business thresholds.

---

## 4. Functional Requirements

### FR-001 — User Identifier (Email / Username)

User must provide a valid email address as their primary account identifier.

Rules:
- Required.
- Must follow valid email format.
- Maximum length is 100 characters.
- Must be unique within the system.

### FR-002 — User Password

User must set and provide a secure password during registration and login.

Rules:
- Required.
- Length must be between 12 and 64 characters.
- Must contain at least one uppercase letter, one lowercase letter, one numeric digit, and one special character (e.g., `@`, `#`, `$`, `%`).
- Whitespace at the beginning or end must be trimmed or rejected.

### FR-003 — Primary Authentication (Login)

User can initiate a session by providing their registered identifier and password.

Rules:
- System validates active status of account.
- Invalid combinations must return a generic "Invalid credentials" error.
- Account must lock temporarily after 5 consecutive failed login attempts.

### FR-004 — Account Lockout & Cooldown

System must enforce account lockout on repeated primary authentication failures.

Rules:
- Lockout threshold is reached on the 5th consecutive failed login.
- Lockout duration is exactly 15 minutes.
- Successful primary authentication resets the failed attempt counter to 0.

### FR-005 — MFA Enrollment (TOTP / Authenticator App)

User can enroll an Authenticator App (TOTP) as an MFA factor.

Rules:
- System generates a secret key and QR code (Base32 format).
- Enrollment requires entering a valid 6-digit TOTP code generated by the app to verify setup.
- Unverified setup tokens expire after 10 minutes.

### FR-006 — MFA Verification (Login Step-up)

When MFA is enabled on an account, primary login must trigger an MFA verification step.

Rules:
- System presents configured MFA prompt (TOTP, SMS, or Backup Code).
- User must enter a valid 6-digit code or an unredeemed backup code.
- User is granted an active authenticated session only after successful MFA completion.

### FR-007 — Backup Codes Generation & Usage

User can generate emergency backup codes upon enabling MFA.

Rules:
- System generates a set of 10 alphanumeric backup codes (8 characters each).
- Each backup code can be used exactly once.
- Generating new backup codes immediately invalidates all previously generated backup codes.

### FR-008 — SMS OTP Authentication

User may opt to receive a verification code via SMS.

Rules:
- Phone number must contain digits only, between 10 and 13 digits.
- SMS OTP code contains exactly 6 digits.
- SMS OTP expires after 3 minutes.
- Maximum incorrect SMS OTP verification attempts allowed is 3.

### FR-009 — Step-Up Authentication for Sensitive Actions

System requires secondary authentication when performing high-risk actions (e.g., changing password, disabling MFA, updating withdrawal details).

Rules:
- Prompts for MFA code even within an active logged-in session.
- Action must be rejected if step-up verification fails or times out.

### FR-010 — Password Reset Flow

User can request a password reset via email link/code.

Rules:
- Reset link/token expires after 15 minutes.
- Reset token must be single-use.
- New password must satisfy password complexity rules (FR-002) and cannot be identical to the last 3 passwords used.

### FR-011 — Session Token Management

Upon successful authentication, the system issues access and refresh tokens.

Rules:
- Access tokens expire in 15 minutes.
- Refresh tokens expire in 7 days.
- Logging out revokes the active refresh token immediately.
- Global logout ("Log out from all devices") revokes all active session/refresh tokens for the user account.

### FR-012 — MFA Disable / Deactivation

User may disable MFA from account security settings.

Rules:
- Requires step-up authentication (current password + active MFA code).
- Disabling MFA invalidates all active backup codes.
- An email alert must be dispatched to the user immediately upon MFA deactivation.

### FR-013 — Replay Attack Prevention

System must prevent re-use of TOTP or OTP tokens within the same time window.

Rules:
- A successfully used 6-digit TOTP code cannot be re-submitted within its 30-second validity window.
- Duplicate submission of the same verification code must return an authorization error.

### FR-014 — Rate Limiting on MFA & OTP Requests

System must protect SMS OTP and verification endpoints from abuse.

Rules:
- Maximum of 3 SMS OTP resend requests per phone number within 10 minutes.
- Repeated calls exceeding rate limits return HTTP 429 Too Many Requests.

### FR-015 — Account State Transitions

Supported user account states:

`UNVERIFIED → ACTIVE → LOCKED → ACTIVE`

Alternative transitions:

`ACTIVE → SUSPENDED`

`ACTIVE → DEACTIVATED`

`ACTIVE → PENDING_MFA` (During login challenge)

### FR-016 — Audit Logging

System must log all security-relevant authentication events.

Rules:
- Events logged: Login Success, Login Failure, Account Lockout, MFA Enrollment, MFA Failure, Password Change, Token Revocation.
- Log payloads must include User ID, Event Type, Timestamp, IP Address, and User-Agent.

### FR-017 — Dependency Failure Handling

Authentication system must safely handle third-party dependency outages (e.g., SMS Gateway, Redis Token Store).

Rules:
- If SMS Gateway fails, user must be offered fallback options (e.g., Backup Code) or clear error messaging.
- System failures must fail closed (deny access) rather than fail open (grant access).
- Account state must remain secure and consistent.

## 5. Non-Functional Requirements

### NFR-001 — Authentication Response Time

At least 95% of primary authentication and token validation requests must complete within 500 ms under normal load.

### NFR-002 — Sensitive Data Protection & Encryption

Passwords must be hashed using Argon2id or bcrypt with appropriate cost factors. Secrets and tokens must never be written in plain text to application logs or persistence layers.

### NFR-003 — Idempotency & Replay Protection

Repeated requests using the same authorization grant or single-use OTP token must not create additional valid sessions.

### NFR-004 — Security & Fail-Closed Behavior

Any unexpected internal error during MFA or credentials evaluation must result in access refusal (fail closed).

### NFR-005 — OTP & Token Security

- OTPs must be cryptographically secure random numbers.
- TOTP time window tolerance must not exceed ±1 interval (30 seconds).

## 7. Key State Model

### Account State

`UNVERIFIED`

→ `ACTIVE`

→ `PENDING_MFA`

→ `ACTIVE` (Authenticated Session Issued)

Alternative transitions:

`ACTIVE → LOCKED` (After 5 failed login attempts)

`LOCKED → ACTIVE` (After 15-minute cooldown or admin unlock)

`ACTIVE → SUSPENDED`

`ACTIVE → DEACTIVATED`

### MFA Setup State

`DISABLED`

→ `ENROLLMENT_INITIATED`

→ `VERIFIED_ENABLED`

Alternative transitions:

`ENROLLMENT_INITIATED → EXPIRED` (After 10 minutes without code verification)

`VERIFIED_ENABLED → DISABLED` (Requires step-up confirmation)

## 8. Decision Table Targets

The following combinations are relevant for testing:

### Login & MFA Validation Flow

Conditions:
- Primary Credentials = Valid / Invalid
- Account Lockout State = Locked / Unlocked
- MFA Status = Disabled / Enabled
- MFA Verification Code = Valid / Invalid / Expired
- Retry Attempt Count = Below limit / At limit

Expected behavior must keep account security state consistent and block unauthorized access.

### Password Reset & Password Reuse

Conditions:
- Reset Token = Valid / Expired / Already Used
- New Password Policy = Compliant / Non-Compliant
- Password History Match = In last 3 passwords / Unique

Expected behavior must enforce validation and password history rules.

### MFA Step-Up & Session Security

Conditions:
- Session Token = Valid / Expired / Revoked
- Action Type = Low-risk / High-risk
- Step-Up MFA Code = Correct / Incorrect

Expected outcome must permit low-risk actions directly while requiring valid MFA for high-risk actions.

## 9. Edge-Case Areas

Relevant edge cases include:
- Leading or trailing whitespace in credentials.
- Boundary values for password length (11, 12, 64, 65 characters).
- Submitting TOTP code right at the boundary of the 30-second time drift window.
- Rapid duplicate submission of the same TOTP/SMS OTP code (race conditions).
- Using a backup code immediately after generating a new backup code set.
- Re-using a password reset link twice within 15 minutes.
- SMS OTP resend requested exactly at the 3rd attempt / 10th minute limit.
- Login attempt on a locked account at 14 minutes 59 seconds vs 15 minutes 01 second.
- Disabling MFA while network drops or SMS provider is unreachable.
- Interrupted global logout token revocation.

## 11. Test Data Guidance

Generated test data should be synthetic and safe for QA use.

Examples may include:
- Email: `user.qa.test@example.test`
- Password: `P@ssword12345!` (satisfies complexity)
- Phone Number: synthetic numeric value satisfying length rules (e.g., `628123456789`)
- TOTP Secret Key: synthetic Base32 key (e.g., `JBSWY3DPEHPK3PXP`)
- Backup Code: 8-character synthetic alphanumeric string (e.g., `A1B2C3D4`)
- OTP Code: synthetic 6-digit value (e.g., `583920`)

For boundary tests, the generator must produce values that actually satisfy the required boundary condition.

## 12. Acceptance Criteria

The Authentication & MFA module is acceptable when:

1. Valid user credentials allow primary authentication to proceed.
2. Invalid email format or password policy violations are rejected during registration/reset.
3. Account is locked out after 5 consecutive failed login attempts for 15 minutes.
4. Active MFA requires valid verification before granting session tokens.
5. Used TOTP and OTP codes cannot be reused (replay protection).
6. Backup codes work once and are invalidated when a new set is generated.
7. Step-up MFA is enforced for high-risk actions within active sessions.
8. Password reset link expires after 15 minutes and prevents re-use of recent passwords.
9. Global logout revokes all active refresh tokens across devices.
10. Rate limits on SMS OTP requests are enforced (max 3 resends per 10 minutes).
11. Dependency failures fail closed without granting unauthorized access.
12. Sensitive information (passwords, tokens, secrets) is encrypted and excluded from logs.
13. Performance requirement is measurable under the stated conditions.
